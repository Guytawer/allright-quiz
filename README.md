Автоматизація квіза реєстрації (Charlie Flow)

Частина А. Стратегія тестування

Головна проблема цього квіза — постійні A/B-тести та зміни порядку кроків. Якщо намагатися покрити його класичним Page Object, де ми зашиваємо жорсткі Крок 1 -> Крок 2 -> Крок 3, то тести будуть падати при кожному оновленні маркетингу. Тому я розділив перевірки за рівнем відповідальності — що перевіряти точно, а що робити гнучко.


1. Що перевіряємо точно, а що робимо гнучким

Точно перевіряємо через API та бекенд:
- Фактичне створення акаунта юзера в базі після заповнення форми.
- Успішне бронювання пробного уроку.
- Відправку аналітичних івентів (GTM/Amplitude) — перехоплюю мережеві запити у момент завершення квіза і перевіряю, що потрібна подія пішла. Якщо відвалиться аналітика — бізнес втратить гроші на прийнятті рішень, навіть якщо сам квіз працює, тому це перевіряємо окремо від UI-флоу.

Що робимо гнучким на UI (через смарт-раннер):
- Обхід самих карток квіза (вік, мова, цілі) — раннеру байдуже, що саме запитують, він просто знаходить доступну опцію і тисне «Далі», поки не дійде до термінального стану.
- Заповнення текстових полів (ім'я, email, телефон) — раннер розпізнає тип поля за атрибутами type/name/autocomplete, а не за конкретним DOM ID і підставляє валідне dummy-значення.

Що взагалі не зашиваємо в автоматизацію:
- Точні тексти й формулювання питань — маркетинг може змінювати їх щотижня.
- Послідовність екранів — вона залежить від A/B-гілки.


Чому тут звичайний алгоритм (rule-based), а не AI-агент

Я свідомо не став підключати сюди LLM для кожного кроку.
Щоб просто вибирати варіанти й тиснути «Далі», розуміти глибокий сенс питань не потрібно — для цього достатньо звичайного аналізу DOM-структури. Якщо на кожен крок викликати нейромережу, це додасть 2–3 секунди затримки на кожне питання, коштуватиме грошей за API-токени й додасть нестабільності (AI може галюцинувати або щоразу обирати різні шляхи).
Використання AI виправдане там, де звичайний код справді безсилий — наприклад, у відкритих полях типу «Напишіть мета навчання вашої дитини», де треба згенерувати осмислений текст. Для стандартної ж навігації звичайний алгоритм працює швидше, дешевше та надійніше. У коді це місце позначено як tryFillTextInputs (generic-fallback).


2. Як раннер розуміє, де «кінець»

Найкрихкіше місце всієї ідеї, тому критерій завершення — не одна ознака, а будь-яка з трьох незалежних:
- URL відповідає патерну завершення (/success, /booking-confirmed тощо);
- у DOM з'явився маркер фінального екрана;
- пішов мережевий виклик на ендпоінт бронювання.

Орієнтуватись тільки на «це форма контактів» небезпечно — в іншому A/B-варіанті вона може стояти не останньою.

Окремо — запобіжник від зависання: якщо за 15 кроків раннер жодного разу не розпізнав відомий патерн екрана, тест падає з RunnerLostError, а не з generic-таймаутом. Це навмисно інший клас помилки, ніж «квіз реально зламаний» (QuizBrokenError) — команда має бачити різницю між «щось нове в A/B, раннер відстав» і «продукт віддає помилку користувачу». Змішування цих двох сигналів в один алерт — швидкий спосіб втратити довіру до сьюту.


3. Як обходити A/B тести

1. Нормальний шлях (через бек): якщо на стейджі можна форсувати варіант через URL-параметр чи куку — фіксуємо потрібну гілку перед тестом. Так покриваємо 1–2 конкретні гілки явно й передбачувано.
2. Фоллбек: динамічний цикл, що оцінює поточний екран і діє за розпізнаним типом. Цей режим навмисно «сліпий» до конкретних варіантів — він і є страховкою від тієї гілки, про яку я не знав заздалегідь.


4. CI/CD

- На кожен PR/коміт: тільки швидкі API-тести (smoke) — доступність ендпоінтів реєстрації/бронювання, без реального UI-проходу і без побічних ефектів.
- За розкладом на Stage: повний UI-прохід (раннер + перевірка бізнес-результату + аналітика) кожні 2–4 години, а не раз на добу — це флоу з платним трафіком, і денна затримка виявлення означає години злитого бюджету. Окремі алерти на QuizBrokenError і на RunnerLostError (друге — привід оновити раннер, а не інцидент на проді).
- Додатково: тригер повного прогону на деплой стейджа як гейт перед промоушеном далі, якщо такий пайплайн є.


5. Побічні ефекти (Data Pollution)

Автотести плодять фейкові акаунти на стейджі. Рішення: унікальні email з часовою міткою (qa_autotest_timestamp@allrighttest.com) + окрема задача на бекенді для періодичного очищення таких юзерів. Ідеально — домовитись з бекендом про прапорець/тег тестового акаунта, щоб він одразу виключався з аналітики й воронки продажів.


Ризики й обмеження підходу

- Раннер не гарантує покриття всіх A/B-гілок одночасно, якщо форсувати варіант неможливо, а рандомізація — на юзера.
- Generic-fallback для freeform-текстових полів («Automated QA response») може не пройти валідацію, якщо на бекенді є смислова перевірка вмісту — це та межа, де вже потрібен LLM-агент.
- RunnerLostError вимагає ручного розбору: чи це новий A/B, який треба підтримати, чи реальний регрес.


Частина B. Реалізація

Реалізовано об'єднаний підхід: агентний (rule-based) прохід квіза до кінця + детермінована перевірка бізнес-результату одразу після завершення. Це не два окремі рішення, а один тест: раннер несе відповідальність за стійкість до A/B, фінальні ерапекти — за те, що результат реально стався на бекенді.


Структура проєкту

src/pages/CharlieQuizPage.ts - динамічний раннер + перехоплення мережі
src/utils/errors.ts - QuizBrokenError / RunnerLostError
src/utils/testData.ts - генерація унікальних тестових даних
src/utils/backendClient.ts - перевірка юзера/бронювання через бекенд
tests/quiz.spec.ts - сам сценарій


Як запустити

npm install
npx playwright install --with-deps

Запуск у фоновому режимі:
npx playwright test

Запуск з видимим браузером:
npx playwright test --headed

Перед запуском скопіювати .env.example -> .env і виставити реальні QUIZ_BASE_URL / QUIZ_BACKEND_API_URL.


Припущення, які я зробив

- Немає доступу до реального internal/QA API стейджа — backendClient.ts — це заглушка з чітко позначеними TODO, яка показує контракт перевірки (пошук юзера за email -> пошук бронювання за userId, з ретраями під асинхронну обробку). У реальному проєкті це перше, що треба погодити з бекенд-командою.
- Не знаю точних data-testid / URL-патернів фінального екрана квіза — в CharlieQuizPage.ts вони винесені в константи вгорі файлу саме щоб їх було легко поправити за 5 хвилин, коли буде доступ до стейджа.
- Не знаю, чи можна форсувати A/B-варіант через query-параметр/куку на стейджі — код розрахований на це, але сам форсинг не заведений, бо не знаю реального імені параметра.


Що зробив би далі за наявності більше часу

- Додав explicit-тест для форсованого A/B-варіанта (control), окремо від «сліпого» фолбек-проходу — щоб мати хоч один повністю детермінований E2E-сценарій.
- Підключив реальний LLM-виклик для freeform текстових полів замість generic-fallback, з окремим прапорцем, щоб вмикати це вибірково.
- Додав job з очищення тестових юзерів на стейджі.
- Покрив дашбордом окремо метрику RunnerLostError — щоб бачити частоту "раннер відстав від A/B" як сигнал для проактивного оновлення евристик.
