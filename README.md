# Автоматизація квіза реєстрації

Агентний прохід квіза реєстрації на stage з детермінованою перевіркою бізнес-результату.
Міркування про підхід — у `part-a-approach.md`. Тут — про код: як запустити, як влаштовано,
що вийшло.

## Ідея в двох реченнях

Агент проходить квіз, не знаючи ні порядку кроків, ні їх кількості, ні текстів. Після
проходу окремий шар перевіряє бізнес-результат: користувач створений, пробний урок
заброньований. Асерти стоять на результаті, а не на кроках, тому зміна A/B-варіанта не
вимагає правок у коді.

Перевірено на обох гілках експерименту без жодної зміни коду. Набори кроків перетинаються
лише частково, порядок різний, у варіанті B після кожного питання йде інфо-екран, у A їх
менше. Кількість кроків плаває навіть між прогонами одного варіанта. Точка входу теж
нестабільна: `/charlie/…` у варіанті B редіректить на `/personalized/…`.

## Запуск

```bash
npm install
npx playwright install chromium
cp .env.example .env      # вписати ANTHROPIC_API_KEY
```

```bash
# агентний прохід до кроку телефону, нічого не створює
npx playwright test agent.spec.ts --headed --project=chromium

# повний цикл з перевіркою результату — СТВОРЮЄ реального юзера і бронь
ALLOW_SUBMIT=1 npx playwright test full-run.spec.ts --headed --project=chromium
```

| Тест | Що робить | Побічні ефекти |
|---|---|---|
| `agent.spec.ts` | агентний прохід до кроку телефону | немає |
| `heuristic.spec.ts` | те саме без LLM — базова лінія для порівняння | немає |
| `full-run.spec.ts` | повний цикл + перевірка результату | **створює юзера і бронь** |
| `api-check.spec.ts` | чи живий ключ і модель | немає |
| `recon-quiz.spec.ts` | розвідувальний скрипт, з якого все почалось | немає |

Змінні: `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` (дефолт `claude-sonnet-5`), `ALLOW_SUBMIT`,
`PIN_VARIANT`.

## Як влаштовано

```
src/
  snapshot.ts        згортання DOM у компактний опис екрана
  runner.ts          цикл проходу, детекція прогресу, стоп-умови, лог тертя
  verify.ts          перевірка бізнес-результату
  solvers/
    heuristic.ts     правила за типами кроків
    llm.ts           модель: та сама задача, але з розумінням змісту
```

Три рішення, на яких тримається решта.

**Солвер — змінна деталь.** Евристика і LLM реалізують один інтерфейс, раннер не знає, хто
приймає рішення. Тому евристика працює фолбеком: якщо API недоступний або відповідь не
парситься, прохід не падає, а продовжується гіршим солвером, і це пишеться в лог тертя.

**Агент вирішує тільки як пройти, не чи пройшло.** Вердикт виносить `verify.ts`, який
нічого не знає про те, хто вів квіз.

**Лог тертя окремо від помилок.** Кожна спроба без прогресу, кожен фолбек пишуться навіть в
успішному прогоні. Агент наполегливіший за живу людину: те, що він пробився, не означає, що
пробився б користувач.

## Що вийшло

Повний цикл до бронювання пройдено на **обох** гілках експерименту, без жодної зміни коду.

Варіант A, 27 кроків, 3.9 хвилини:

```
POST  /api/v1/users        → 200    користувач створений
PATCH /api/v1/users/851806 → 200    профіль оновлений
POST  /api/v1/lessons      → 200    пробний заброньований
```

Варіант B, 21 крок, 2.6 хвилини:

```
POST  /api/v1/users                    → 200
PATCH /api/v1/users/854159/update-email → 200
PATCH /api/v1/users/854159              → 200
POST  /api/v1/lessons                   → 200
```

Шляхи різні не тільки кількістю кроків. У варіанті B є окремий крок вводу email
(`user-info-email`), якого в A немає, і після телефону він веде одразу до вибору часу.
У варіанті A після реєстрації агент потрапляє на дашборд, звідки до бронювання ще треба
дійти — і саме там ховається кнопка «Перший місяць безкоштовно», яка веде в оплату.

Перевірка в обох випадках зійшлася на п'яти незалежних доказах: сесія в localStorage, два
успішні POST на API продукту, перехід у кабінет, текст підтвердження на екрані.

Токени: 24 700–31 700 вхідних на повний цикл з бронюванням залежно від варіанта, близько
9 000 вхідних на прохід без нього. Виходить приблизно 1 100 вхідних токенів на крок.

### Де LLM виграв у евристики

Обидва солвери ганялись на тих самих екранах, різниця тільки в тому, хто приймає рішення.

| Крок | Евристика | LLM |
|---|---|---|
| Попап «хто заповнює анкету» | застрягала намертво: заповнювала перекрите поле під модалкою по колу, 3 спроби і стоп | обрала «Я — мати або батько» |
| Формат телефону | немає механізму переформулювання | `0931112233` не пройшов → сама підставила `+380 93 111 2233` |
| Мультиселект хобі | тикала опції наосліп, стабільно один запис тертя | обирала кілька одразу, тертя нуль |
| Дашборд після реєстрації | правил для цього екрана немає | «Уникаю кнопки *Перший місяць безкоштовно*, оскільки це веде до оплати» |

Останній рядок вартий пояснення. У першому повному прогоні ціль у промпті була
сформульована як «заверши реєстрацію» — і агент сумлінно доїхав до екрана оплати підписки
на 24 160 грн, зачепивши `POST /api/v1/transactions`. Кнопка виявилась неактивна, тому
платіж не пішов. Після цього ціль звужена до безкоштовного пробного, заборони поставлені в
промпті явно вище за мету, і додано безумовний стоп на платіжних екранах — він працює навіть
з `ALLOW_SUBMIT=1`, бо дозвіл створити юзера не є дозволом платити.

## Знайдено по ходу

**Autoplay блокує квіз.** Персонаж програє відео без `muted`, і перехід на наступний крок,
схоже, зав'язаний на подію `ended`. У браузері із заблокованим автоплеєм `play()`
відхиляється і застосунок показує «Помилка завантаження». У тестах обходиться прапорцем
`--autoplay-policy=no-user-gesture-required`, але це зачіпає і реальних користувачів.

**Капчі й OTP на шляху немає.** `check-captcha` віддає 200, крок телефону проходиться без
коду.

**Пінінг варіанта через `localStorage` не працює.** Значення записується до завантаження
сторінки, але застосунок перезаписує його при старті: три прогони з `PIN_VARIANT=A` дали B.
Тобто `experiments` — дзеркало рішення, а не механізм керування, і відтворити конкретний
варіант зараз неможливо.

**Події воронки не відповідають крокам один-до-одного** — 20 подій Jitsu і у варіанта з 14
кроками, і у варіанта з 12.

## Припущення

Питання команді відправлені, відповідей на момент здачі немає.

1. **Верифікація** — по слідах у браузері: сесія, успішні POST на API продукту, стан UI.
   `ApiOutcomeVerifier` лишений заглушкою — це точка підміни, коли з'явиться доступ до API.
2. **Тестові дані** — патерн `qa-agent-<timestamp>@example.com`. Без узгодженої конвенції
   реєстрації, ймовірно, потрапляють у продуктову аналітику.
3. **Cleanup не реалізований.** За час роботи на stage створено кілька користувачів і
   принаймні одну бронь, email є в логах прогонів.
4. **Слаги кроків** — тільки в логах. Спроба зробити на них стоп-умову провалилась: у
   варіанті A слаг кроку телефону інший, і агент проїхав повз запобіжник. Замінено на
   змістову ознаку — поле з `type="tel"`.
5. **Rate limits не враховані** — прогін розрахований на невелику кількість запусків.

**Вибір часу — найслабше місце.** У трьох повних прогонах поспіль модель не могла клікнути
слот з першого разу: два-три невдалі кліки, перш ніж бронювання проходило. Календар
віддається агенту гірше за всі інші екрани — там багато схожих елементів і неочевидний
порядок дій (спершу дата, потім час, потім підтвердження).

## Обмеження й що далі

Детально — в `part-a-approach.md`, розділи «Що тут може піти не так» і «Що зробив би далі».
Найкоротше: детекція модалок тримається на `role="dialog"` і в решті випадків не працює
(це лікується не хитрішою евристикою, а домовленістю про `data-testid`); пояснення моделі в
логах не можна читати як опис того, що вона зрозуміла; фолбек зараз тихий, тому прогін, у
якому модель не відпрацювала жодного разу, все одно зелений.
